# 实现架构概览

框架维护“谁能让哪个岗位，在什么工作里，以什么能力，读取哪些资料并完成什么动作”。行业语义通过插件与适配器接入。

| 层 | 代码位置 | 责任 |
| --- | --- | --- |
| 可信宿主 | src/index.ts、server.ts及organization等模块 | 身份、公司范围、组织授权、管理接口 |
| 工作内核 | work、work-control、work-actions、work-continuity、tasks | 持久工作、队列、轮次、停止、恢复、回执、核实 |
| 能力系统 | plugins、plugin-sdk、plugin schema、packages | 插件注册、健康、工具符合性、精确版本、受控宿主服务 |
| 记忆 | memory及上下文组装 | 按岗位授权、INDEX索引、笔记版本、按需读取与预算 |
| 推理与执行 | runtime、harness-profile、harness-client及连接器 | 将获准能力交给Harness或远程适配器，限定工具与预算 |
| 模型与连接 | channels、connections等 | 渠道配置、凭证解析、并发与用量归属 |
| 员工会话 | client/company-session、desktop | 内部账号、设备身份、岗位切换、原生Host生命周期 |
| 管理展示 | web及web/studio | 使用真实API配置与查询；studio是显式视觉配置 |

## 身份与权限

员工账号、执行岗位与模型渠道是三个不同对象。公司可以统一管理模型Key，但每次执行仍记录员工、岗位和工作，不把所有员工伪装成同一个身份。员工工具授权与岗位工具授权都必须满足，插件清单只能申请能力。

团队查看/派工/核对和私有记忆访问分别校验。部门上下级不是操作系统级进程父子关系，也不是“上级自动拿到所有下级上下文”。

## 插件与Harness的关系

框架插件插座由manifest、JSON Schema和协议组成；适配器再将获准能力绑定到Harness。它没有把本框架清单冒充Harness原生包。Harness放在执行及交互层，不掌握公司数据库和账号授权。

文档核对与库存比对验证“同样的内核，不同能力包”。接入财务、获客、销售、视频等业务时，应添加独立能力包及外部系统引用，不新增内核行业字段。

## 状态、记忆与恢复

PostgreSQL是权威状态。Markdown是记忆的可查看副本；日志和报告不自动全部注入上下文。每个Agent先读取索引，再拿当前任务需要的内容。

工作保留轮次与人工决定，停止后关闭新动作准入，已开始动作等待收尾。已经确认的相同动作复用回执；未知外部结果不能自动重放，必须先核实。恢复是有明确要求的新轮次，不抹掉旧记录。

## 目前的边界

总体设计1.1还包含分级回传、共享知识发布和增量聚合等后续建设要求，不能把设计文档当作完成清单。插件进程隔离尚不等同完整系统沙箱；外部业务写操作需要单独审批及业务侧幂等。生产高可用、正式签名发行、自动升级和企业消息实机联调都应有独立验收。
