# 远程回执测试的随机端口故障 · 2026-11-15

## 原因与复现

原失败表现是两项回执测试得到`RESULT_UNKNOWN`，但服务端处理次数为0。测试期望的是请求已到达服务端后回执丢失或缺少运行标识，因此处理次数必须为1。

测试使用`listen({host:'127.0.0.1',port:0})`，默认认为操作系统分配的端口都能通过`fetch`访问。本机Windows的IPv4/IPv6动态TCP端口范围为1024至15000，其中包括Fetch禁止的6667、6668等端口。端口能监听不代表Fetch允许连接，参见[Fetch标准的端口限制](https://fetch.spec.whatwg.org/#port-blocking)。

在相同运行时把两个测试服务分别绑定到6667和6668，可稳定得到原来的两项失败：底层`TypeError`的原因是`bad port`，请求尚未发出，服务端处理次数为0。对同一端点使用Node原生HTTP请求，分别得到503和200，服务端处理次数为1。原始失败日志没有保存实际端口，无法倒推出那一次分配值；本次确认并消除了能够稳定复现相同症状的端口分配缺陷。

框架把不可确认的执行回执保守地归为`RESULT_UNKNOWN`，这一行为仍然保留。修复不放宽未知结果恢复条件，也不自动重放远程动作。

## 修复

- 新增测试专用`tests/helpers/http-server.ts`，直接将真实HTTP服务绑定到回环地址的49152至65535端口。
- 最多尝试32次；仅在端口占用或操作系统拒绝绑定时换端口，应用启动错误原样抛出。没有“预先占位后释放”的端口竞争窗口。
- 将17个文件中的36处Fastify HTTP测试监听统一接到该辅助函数，避免同一原因转移到其他HTTP集成测试。
- 两项原断言继续要求服务端只处理一次；丢失回执测试额外核对503对应的错误原因。
- 新增真实HTTP处理、端口被占用时保留原服务、拒绝不安全端口和传播启动错误的回归覆盖。原生WebSocket测试不通过Fetch，继续使用其独立的随机监听。

修改限于测试与说明，不修改业务内核、员工数据、系统端口设置或线上配置。
