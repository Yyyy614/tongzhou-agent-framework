# 工作连续性 A1：显式继续与返工

本段对应设计1.1阶段A的第一个闭环，不是阶段A整体完成。基线差距见DESIGN_GAP_AUDIT.md。

## 当前契约

- POST `/v1/work/:id/inputs`：`revision`、`idempotencyKey`、`assignments[{agentId,prompt}]`。202回执返回workId/inputId/round/controlRevision/taskIds/checkpointRef；accepted表示持久受理，不表示已执行或验收。
- Bot `/v1/bot/messages` 可附workId和revision；两者必须同时提供，身份仍来自已鉴权入口。未附这两个字段时保持旧独立消息行为。
- GET `/v1/work/:id/history` 返回轮次、任务/Run引用、输入来源、审核与交接快照引用，不默认返回所有prompt/长结果。GET `/v1/work/:id/inputs/:inputId`用于明确按需读取一条输入。
- 工作详情增加currentRound/controlRevision；旧Work第1轮/controlRevision=0，旧结果revision算法和旧审核API保持兼容。
- TypeScript调用方可从框架根入口导入WorkInput、WorkInputReceipt、WorkEntry，接入方无需依赖内核数据库或猜测受理回执结构。

仅上一轮全部任务succeeded、处于waiting_review/changes_requested/completed时可以显式继续。执行中、失败、等待批准、取消或结果未知不自动续办，也不重放原任务。每工作最多32轮，每次仍受1–8岗位和原有工作预算限制。后续轮可选择原参与岗位的子集；不能通过补充输入把新参与者加入工作。

新轮从原始任务继承budgetGroupId，包括原工作与其他协作共享总预算的情形；不因为新轮次改用新的预算组。原记录预算归属不一致时拒绝继续并要求核实。

受理与新Task排队处于同一事务；幂等键重复返回同份回执，内容变化或旧revision冲突。每轮重新检查当前公司、阅读范围、派工权和原来源Agent委派范围，记录宿主生成的受理授权/配置摘要。队列准入及繁忙重试时再次检查；配置变化后拒绝执行，不静默采用新能力。

插件发起的工作在A1继续沿用原source Agent所有者和delegates约束，其他负责人/管理员不能仅凭team.dispatch代替原来源主体。跨负责人接管需要后续显式受托/受理策略；本轮没有隐式扩大该权限。

## 历史与交接快照

原work_assignments保留第1轮，新表work_round_assignments保存后续分配，current_round只切换当前视图；不覆盖旧Task/Run终态和prompt。work_review_history归档旧审核，旧审核不能自动批准新轮次。work_inputs登记来源和新要求；controlRevision目前只计数已受理输入，完整停止/人工控制代数属于A2。

进入下一轮时，work_checkpoints只保存宿主确认的前轮任务状态、Run和结果引用。新Worker的`work_checkpoint`工具按当前所有者权限，只读取本人前轮结果片段（最多2000字符，明确截断）和回执引用，读取另有审计。不会自动把旧聊天或其他岗位完整结果塞入模型。完整历史/输入需要当前有权阅读全部原参与岗位；不等于自动获得他们的私人记忆。

这是一份已确认终态的交接快照，不是供应商内部推理或任意外部动作的可恢复事务。执行中补充、停止优先、未知结果核实和细粒度资源/摘要ACL仍未完成。

## 本机隔离体验与QA清单

`node --env-file=.env scripts/start-work-continuity-demo.mjs` 使用127.0.0.1:4517、.local/design11-a1/host及独立数据库schema；脚本显式要求项目本地PostgreSQL，不采用环境中的云端数据库URL。管理员/负责人令牌和短时入口仅写入此隔离目录，不覆盖原.local/access.json。

后台“协作工作”新增轮次、继续/返工和历史按钮。旧宿主未返回currentRound时不显示这些扩展。本人旧结果按需读取由SDK执行适配器验证，现有云端员工软件和原生安装包本轮没有更新。

验收清单：

1. 原工作初轮完成→人工要求调整→后台受理新轮→新任务执行→Bot跟进原工作→历史保留多轮与审核。
2. 6次并发重复输入只排队一次；不同输入复用键和旧revision返回409；两次Host重启后待办执行一次且旧结果保留。
3. 跨公司/越权历史拒绝，补充不能扩原参与者或伪造身份；配置在繁忙准入中变化后不执行；活跃/未知结果不能被新输入替换。
4. 真实SDK+受控模型检查最终请求：新Run不携带旧原始消息，调用本人checkpoint后才获得所需旧结果；这不是原生聊天C08整体隔离完成的声明。
5. 后台用普通点击验证继续、历史、审核，旧revision冲突保留编辑草稿；检查窗口排版和中文状态，技术ID默认折叠。
6. 真实模型验证与受控provider测试分别记录；服务不连接旧schema，不部署或重启服务器，不修改原设备数据。
