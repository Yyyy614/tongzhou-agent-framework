# 当每个员工都有自己的 Agent，公司该怎样协作？

这段时间，我一直在想，公司真正用上 AI 以后，会变成什么样。

一开始，我想到的东西其实挺碎。员工能不能有自己的账号和 Agent？不同部门能不能配置不同的能力？上级怎样了解下级的工作？员工做出一个好用的 Skill，能不能放到公司内部，让其他人也用起来？

再往后想，还会有更多具体的问题：工作做到一半换一个人，Agent 能不能帮忙交接；事情出了问题，能不能及时找到负责人；领导想了解进度，能不能直接看到有依据的结果；同事今天积累下来的方法，过一段时间还能不能找得到、用得上。

这些需求看起来分散，但我慢慢发现，它们都指向同一件事：**当员工各自有了 Agent，整个组织应该怎样协作。**

我把现在这个尝试叫作“同舟”。我想做的是一套通用的企业 Agent 协作框架，也用自己的公司需求来验证它。

## 从一个人的效率，想到一群人的协作

我看到不少 AI 在工作中的使用，都是从个人开始的。写文案、查资料、做表格、写代码，每个人都可以把自己的流程优化得更好。

这当然有用。但一件工作从一个人走到另一个人那里，仍然需要反复解释：前面做了什么，为什么这样决定，还有什么问题，下一步应该找谁。

管理者也要不断问进度。员工完成工作以后，还要花时间重新整理，才能变成一份别人看得懂的汇报。

我就会想到，如果 Agent 已经参与了这个过程，它是不是可以顺便把这些必要的信息留下来？事情发生变化时，能不能把需要知道的部分交给下一位负责人？到了需要汇报的时候，再根据已有记录整理，而不用让人从头讲一遍。

当然，记录不完整的时候，AI 也不能凭空知道所有事情。我想要的，是让工作过程更容易被接续、被核对，而不是让一个模型替大家编出一份看起来很完整的报告。

如果往后再走一步，我觉得会出现越来越多 Agent 与 Agent 之间的协作。我之前把它叫作“AtoA”，这里泛指 Agent 之间的工作交接和配合，具体落地仍然需要共同的规则、权限和接口。

## 我会把公司理解成一个有分工的整体

想这些事情的时候，我经常会想到分工。

一个人独立完成所有事情，能做的范围毕竟有限。形成群体以后，大家各自负责一部分，通过协作完成更大的事情。公司里的部门和岗位，也可以从这个角度理解。

比如一个宣传部门，里面可能有内容、设计、视频、活动等不同的工作。我们把这些能力组合起来，就形成了一个能承担相应职责的部门。

我觉得“封装”这个词很适合用来描述其中的一部分。

沿着这个类比继续想，语言帮助人交换想法，道路和网络又把协作范围扩大。Agent 出现以后，我希望交接时能直接带上工作状态、产出和证据，让对方更容易接着做，而不只是听完一段解释后再重新整理。

以前我们说把一个岗位的方法整理出来，通常会想到 SOP：遇到什么情况、按什么步骤、用什么资料、交给谁核对。有了 Agent 以后，这套方法还可以连上工具和接口，进一步变成能够执行、能够留下结果的工作能力。

然后，多个这样的能力又可以组合起来，承担更完整的工作。

这里封装的是方法和能力。人仍然需要处理判断、例外和责任；岗位也会不断变化。我希望框架能让人更容易调整自己的做法，把有效的方法沉淀下来。

我也会想到自己熟练打字的时候。我关注的是要表达什么，手上的动作会自然衔接，不会每一下都先想清楚应该按哪个键。这个比喻让我觉得，一个协作系统里，每一部分应该掌握自己需要的信息，做好自己负责的事。

统筹者需要看清目标、关系和异常，执行者需要掌握当前工作的条件与细节。这样大家才有可能共同组成一个有效运转的整体。

## 统一的“插座”，让能力能够不断加入

在这方面，DeepSeek Harness 的插件化设计给了我很直接的启发。它以“一切皆插件”的方式组织能力，这也是我选择它作为运行与交互基座的重要原因。[DeepSeek Harness 项目](https://github.com/deepseek-ai/deepseek-harness)

我之前用过一个很直观的说法：插头和插座只要遵循同一套标准，新的电器就可以接进来。

我希望自己的框架也能这样。以后开发出新的工具、接入新的服务，或者整理出一种新的岗位工作方式，都能通过明确的接入标准加入，而不用每次从账号、权限、记忆、日志重新做一遍。

对后续开发和维护，我也有类似的期待。扩展一个模块时，应该能查到它的接口、输入输出、授权要求和相关资料；修改这部分能力，尽量把影响限定在明确的边界内。这样，框架和业务可以持续往前走，开发者也更容易找到自己真正需要理解的部分。

举个例子，一个能力可以负责取得外部信息，另一个能力负责继续处理，后面再进入交付或核对。业务可以换，工具也可以换，工作应该仍然有清楚的归属，数据应该仍然能按权限串起来。

所以，我一直强调这些业务案例是用来验证框架的。最终希望留下来的，是可以换到其他业务里继续使用的共同机制。

技术上，这里也有几种不同的东西：工具插件、Skill、岗位预设、界面扩展、外部 MCP 服务。它们各有用途，需要通过适配接进来。框架共同管理的是身份、能力授权、工作关联、来源和结果。

## Agent 要能接住工作中发生的变化

后来我读到《Super-agent 设计探索：迈向更自主的 Agent 系统》，里面关于持续接收事件、分派执行，以及按引用逐步找回上下文的讨论，让我对这个方向有了更具体的理解。[Super-agent 原文](https://mp.weixin.qq.com/s/zoS7GlReWPhfCjENGxXCdg)

我觉得这样的辅助方式，在日常工作里也有很多应用空间。

系统里发生了变化，Agent 可以先判断是否需要处理，找到对应工作和负责人；在已经授权的范围内做辅助准备，把需要人决定的部分留下来。一个约好的跟进时间到了，也可以带着必要背景提醒相关的人。

要做到这些，前提是接通真实的资料和接口，把触发条件、允许的动作和核对责任定义清楚。

我希望它逐渐成为一个能持续辅助工作的 bot：人有明确指令时，它能接；已有工作出现新情况时，它也能接得住。

这个过程可以概括为：

> 变化发生 → 判断来源与权限 → 找到所属工作 → 读取必要信息 → 执行允许的动作 → 留下回执与结果 → 交给下一位负责人或等待核对。

尤其重要的是“所属工作”。同一个群里可能讨论几件事情，同一件事情也可能出现在不同入口。框架需要识别可靠的关系；不确定的时候，就让人选择和纠正。

## 记忆应该按需展开

公司长期使用以后，资料和历史一定会越来越多。

我最初想到的资料，大致有几类：公司做什么、产品和文化这些基础信息；订单、审批、工作安排、组织关系等内部记录；以及一段时间的工作日志、报告和积累下来的经验。

但这些分类还不够。每一份资料还需要知道谁负责、谁能读、哪个版本有效，以及和什么工作有关。

我一直希望每个 Agent 有一份像笔记库那样能索引、能链接、能维护的独立记忆。这里我会想到 Obsidian 的使用方式：先知道线索在哪里，需要时再顺着关系去看。

一个岗位平常做好自己的事情，就不必每次处理整个公司的资料。负责人平常看进展和异常，需要追查某项工作的依据时，再逐层展开。

Anthropic 对即时检索和渐进式上下文展开的讨论，也提供了可以参考的方法：先保留轻量入口，执行时再取得相关内容。[上下文工程文章](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

在同舟里，我们把它落成了可见资料域、资源索引、有限片段和继续读取的引用。当前工作的目标、决定、阻塞和下一步，单独保存；历史可以保留在外部，需要时再查。

这里有一个我后来越来越重视的区别：存下来、登记到索引、通知别人、送进模型上下文，是几件不同的事。

一份过程文件可以保存在公司服务器上，但没必要因此复制给每一级负责人。上级可以先收到必要状态、结果摘要和成果引用；查看详情时，仍然要按权限读取。

这样，中枢才能掌握组织的运行情况，各个 Agent 也能保留独立的工作范围。

## 个人的方法怎样变成组织的经验

我也希望员工能够定制自己的 Agent。

同样一个岗位，不同的人会有不同习惯。某种回复方式不合适，可以调整自己的偏好；某个步骤容易出错，可以记录下来；做出了好用的小工具或 Skill，也可以提交到内部市场。

但经验要分享给其他人使用，就需要有验证、审核和版本管理。个人的一次判断，不能直接成为整个公司的默认规则。

我想要的路径是：先记录，再形成候选，经过验证和审核，在合适的范围里发布；使用以后继续收集反馈，必要时修订或停用。

员工可以不断优化自己的做法，公司也能从实际工作中积累更好的方法。模型能够辅助整理，管理员和负责人仍然要对规则、权限和发布负责。

统一更新也是这套机制的一部分。员工应该清楚自己正在使用哪个版本，公司能按范围发布和撤回能力，问题出现以后也能找到依据。

## 同舟现在怎样实现这些想法

目前我把整体分成几部分。

员工使用的是公司版 Harness，在应用里登录账号、选择自己的岗位，进入对话和工作中心。岗位可以有不同预设，挂载不同的已授权能力。

公司宿主管理账号、组织权限、工作状态、资料来源、记忆、插件发布、日志和模型用量。员工各自有身份和使用记录，公司可以统一配置模型渠道，不需要让所有人共用一个员工登录身份。

具体业务通过插件和连接器加入。需要处理一件工作时，宿主先确定身份、工作和权限，再组织必要上下文，交给 Harness 执行，最后保存回执和成果引用。

同一套机制可以部署在云端，也可以部署在公司的服务器上。员工连接公司的服务地址，资料按公司的规则保存。使用外部模型时，本轮推理所需的内容仍会发送给模型服务；完全离线需要另外准备内网模型和相应能力。

我希望这套框架既能管理持续工作的 Agent，也能让员工在自己的电脑、企业消息入口中使用它。部门上下级表达的是责任和授权，真正的工作关系可以跨部门连接。

项目地址：[同舟 · Tongzhou Agent Framework](https://github.com/Yyyy614/tongzhou-agent-framework)。

## 已经跑通了什么，还需要继续验证什么

目前项目是 0.8 隔离预览版。账号与岗位、插件挂载、独立记忆、跨 Agent 派工、结果核对、来源权限、事件关联和用量记录，都已有可运行的实现。

0.8 对应的代码验证中，类型检查、构建和 223 项测试通过。长期记忆的合成验证做了 1001 次笔记保存，确认历史来源增长时，当前上下文仍能保持有限；这个实验只有少量受控模型请求，不能据此说明长期自主工作已经成熟。

现在仍有不少事情要继续做：真实资料里的召回质量，复杂事件的归属，多人同时工作时的性能，旧数据迁移，统一更新，以及真实企业消息平台的收发。当前执行和来源核验也有明确上限，超过范围会要求进一步核实。

我目前能说的是，这些想法已经有了可以运行和检验的框架基础。

至于一家公司到底怎样才算“AI 化”，我觉得还需要在使用中继续回答。对我来说，一个很具体的检验方式是：工作换一个人接手时，他能不能顺利继续；负责人想了解进展时，能不能找到真实依据；大家积累的方法，能不能在下一次工作里发挥作用。

我希望同舟能沿着这些问题继续往前走。

- [Anthropic：Effective context engineering for AI agents](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)：为轻量引用、执行时检索和逐步展开上下文提供参考。同舟目前采用自己的资料与授权契约实现这些机制。
